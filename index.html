Authorisation is where the money is

Most application security work rewards breadth. I went the other way. Injection and XSS get caught by tooling and by the second reviewer; access control does not, because a server has no way to know that a perfectly well-formed request came from the wrong person. That is the gap I've built a career in: IDOR and BOLA, privilege escalation, tenant boundaries, session handling, and the business logic that sits underneath a checkout or a permissions model and quietly assumes everyone plays fair.

The work is manual by necessity: map the surface, enumerate every role, then replay every state-changing request as every other identity. It is unglamorous and it finds criticals. I'm currently adding infrastructure depth in Windows, Active Directory and enterprise network testing through OSCP preparation.

Field note

Why compute platforms break differently

On most SaaS products a plan limit is a commercial boundary. Bypass it and you get a feature you didn't pay for. On a compute platform the limit is the product. Behind it sits a finite pool of real machines, shared by every tenant, handed out by a scheduler with no opinion about who deserves them. Break that limit and you aren't taking a feature. You're taking the platform's inventory away from everyone else on it.

The bug

The target sold scheduled access to HPC and GPU nodes for scientific computing. Free-tier accounts were capped at one running job and ten nodes. Both caps were enforced in the interface. The API underneath enforced them too, but per request, against a counter it read and then acted on.

POST /api/v1/jobs · free tier · cap = 1 job / 10 nodes
POST /api/v1/jobs HTTP/2
Content-Type: application/json

{ "node_count": 1000 }   ← sent x200, concurrently

Why every request passed

Concurrent arrivals · one shared counter
req #1reads jobs_running0 → accept
req #2reads jobs_running0 → accept
req #3reads jobs_running0 → accept
…all read before any writes0 → accept
expectedsecond request sees the first1 → reject

Fired in sequence, request two would have been refused. Fired together, every one of them read the same zero. Time-of-check to time-of-use: the validation logic was correct, and the window between checking and committing was unguarded. The node_count tampering rode along on all of them: ten became a thousand, two hundred times over.

What actually broke

Not free compute. An outage. The scheduler accepted hundreds of oversized jobs it could never place, queued work stopped moving, applications failed to launch, and the platform returned 500s to every user until it was manually rebooted. A quota bug on a compute product is an availability bug for everyone sharing the pool. The blast radius has nothing to do with the account that triggered it.

Why this class keeps getting more expensive

Every AI product shipping right now is a compute broker wearing a different interface: GPU-hour budgets, token allowances, inference concurrency caps, agent job queues, sandbox spawn limits. In each of them the quota is simultaneously the billing boundary and the capacity boundary, which makes one unguarded counter both a revenue leak and a denial of service. The pattern spreads because the naive implementation (read the count, compare it, insert the row) is what almost everyone writes first, and it passes every test that doesn't run two requests at once.

Where the check belongs. Enforcement has to live where the state lives: an atomic increment, a conditional update, a unique constraint on the reservation. Anything that makes the datastore refuse the second write rather than trusting application code to have counted correctly. Rate limiting in front of the endpoint narrows the window; it does not close it.
